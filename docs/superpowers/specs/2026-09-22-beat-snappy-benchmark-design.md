# Design: PolyFoamMesh vs snappyHexMesh — Benchmark and Reliability

Date: 2026-09-22
Status: APPROVED (design sections) — awaiting spec review, then implementation plan
Constraint: **local-only work — no push to GitHub, CI/release untouched**

## Goal

Increase the reliability of PolyFoamMesh meshing algorithms (cfMesh hex,
tet→poly + BL, GMSH direct) with the stated objective of beating
snappyHexMesh. Success is defined as: absolute quality thresholds met AND
equal-or-better metrics than snappy on the same corpus.

The long-term "beat snappy" claim belongs to `.opencode/GOAL.md`; this
project's deliverable is narrower (see Done criteria).

## Section 1 — Scope and corpus

**In scope**
- Comparison harness: our 3 pipelines × 2 snappy baselines on the declared corpus
- Terrains A (quality), B (reliability/failure recording), C (robustness)
- Post-baseline algorithm improvement lanes driven by measured gaps

**Out of scope**
- Any push/remot; CI (`.github/workflows/`) and release workflow not modified
- Historical valve fixture runs (>25 min) not in corpus
- Changing mesher defaults without opt-in flags (existing repo rule)

**Corpus (~10 geometries, every run ≤25 min, target ≤10 min where possible)**

| # | Geometry | Origin | Terrain |
|---|---|---|---|
| 1 | Cylinder | existing | sanity / A |
| 2 | Cube-duct | existing | sanity / A |
| 3 | Groove1 | existing | A/B |
| 4 | Slot1 (thin slot) | existing | A/C |
| 5 | Venturi | existing | A/B |
| 6 | Mini-valve | new (scaled-down valve within budget) | B/C — historical concave case, scaled |
| 7 | Ultra-thin gap channel | new | C — addLayers stress (snappy notably weak) |
| 8 | Concave bracket (C/L re-entrant + fillet) | new | C — re-entrant concavity |
| 9 | Dirty CAD: unsolved surfaces / non-watertight hole | new | C — declared snappy-hostile |
| 10 | Multi-inlet manifold | new | B — patch roles / selective BL |

- Geometries 6–10 are generated by the agent (versioned scripts under
  `benchmarks/`, deterministic STLs).
- A geometry enters the corpus only if `pipeline + checkMesh` completes
  **within 25 min** on its tier; otherwise scaled down or excluded with a note.

**Tiers**
- **fast** (regression gate): geometries 1–5 + 7, target ≤15 min for the whole tier
- **full** (leaderboards, decisions): entire corpus, manual, ≤25 min per run

## Section 2 — Harness and leaderboards

**Location**: extend `benchmarks/`, reusing `run_benchmarks.py` structure
(same JSON result format, same checkMesh parsing from
`core/openfoam_runner.py`). New modules:

- `benchmarks/snappy_baseline.py` — snappy case builders (base + expert)
- `benchmarks/run_comparison.py` — the comparison runner
- `benchmarks/compare_snappy.py` — leaderboard/report generator

**Runner** (`benchmarks/run_comparison.py`):
1. For each geometry × runner (3 ours + snappy-base + snappy-expert): prepare
   case under `C:/cfmesh_bench/` (no spaces), mesh with **1500 s (25 min)
   timeout** — timeout = recorded failure (terrain B)
2. Run checkMesh; extract: non-ortho max, skew max, aspect max, negative
   volumes, cells, per-stage total time
3. Write `benchmarks/results/comparison_<timestamp>.json` (one record per
   run: outcome, metrics, errors)

**Snappy baselines** (`benchmarks/snappy_baseline.py`):
- **base**: blockMesh from bbox, canonical snappyHexMeshDict — pure surface
  refinement (`nCellsAcross≥3`), `addLayers` with OpenFOAM manual defaults,
  castellated/snap/addLayers sequence
- **expert**: `extractFeature` feature edges, 2 refinement levels (surface +
  feature), curvature-based refinement, tuned `addLayers`
  (`expansion`/`minMedialRatio` per geometry), high `resolveFeatureAngle`
- Both configs are **versioned templates** — expert snappy is reproducible,
  not hand-tuned per run

**Leaderboards** (`benchmarks/compare_snappy.py --report`):
- Per-terrain table: geometry × 5 runners → metrics + ✅/❌ absolute
  thresholds + winner per cell
- Aggregates: % runs passing absolute thresholds (B), median metrics per
  runner (A), list of geometries where snappy fails and we don't and vice
  versa (C)
- Output: JSON + readable Markdown (`benchmarks/results/LEADERBOARD.md`)

**Absolute thresholds** (derived from `core/quality_thresholds.py`, single
source of truth): `non_ortho ≤ 70`, `skew ≤ 4`, `aspect ≤ 1000`,
`0 negative volumes`, checkMesh `Failed N` ≤ 1 with N ≠ negative volumes.
Applied to **all** runners, snappy included.

**Fast gate**: `python benchmarks/run_comparison.py --tier fast` → nonzero
exit if one of our pipelines drops below absolute thresholds (regression) —
local only, **not** wired into CI.

## Section 3 — Improvement lanes and verification

**Decision flow** — results decide, not hypotheses:

1. **Gap analysis**: extract significant gaps from the report (ours below
   absolute thresholds, or clearly worse than snappy on a metric/geometry),
   ordered by severity (negative volumes > non-ortho > skew > aspect > time)
2. **One lane per gap cluster** — likely candidates given documented state:
   - *BL lane*: slots/concavities where prisms collapse → optimize
     `decoupled_vertex`, throat reduction, patch selection
   - *tet-poly lane*: pyramid/non-ortho defects on the dual → smoothing,
     collapse, dualization criteria
   - *hex/cfMesh lane*: sizing/feature detection on dirty CAD — where snappy
     wins on snap
   - *Robustness lane*: non-watertight geometries → fault-tolerant/repair
     before meshing
3. Each lane follows repo discipline: **prediction written first**
   (`notes/*_reasoning.md`), patches **opt-in flags or no default change**,
   A/B measured on **fast tier** first then **full**, result documented in
   `residual_risks.md` or the leaderboard itself
4. After each lane: regenerate leaderboard → gap closed = lane closed; else
   iterate or declare a kill (existing practice: "measured no-op, not
   promoted")

**Verification**
- Harness: pytest for record parsing, winner computation, fast-gate exit
  code (JSON fixtures, no WSL in fast tests)
- Runtime: manual fast-tier smoke test; full tier before declaring baseline
- **Done criteria** (this project): complete baseline leaderboard + written
  gap analysis + at least one lane started with documented A/B — *not*
  "beat snappy" (that is the long-term GOAL)
- Invariants: ruff green, pytest `-m "not slow and not wsl"` green, no
  default changed without a flag, no push

## Risks

- **Snappy expert config quality**: a weak expert config invalidates the
  claim. Mitigation: versioned templates + OpenFOAM docs best practice;
  double leaderboard (base + expert) keeps the naive comparison honest.
- **Budget overshoot**: some new geometry may exceed 25 min on some
  pipeline. Mitigation: entry rule (scale down or exclude with note).
- **Corpus bias**: existing geometries 1–5 were used for tuning history.
  Mitigation: new geometries 6–10 are fresh and never used for tuning.
- **Mini-valve fidelity**: scaling the valve down may lose the concave
  defect class. Mitigation: verify the scaled case still exhibits
  documented concave/pyramid defects before accepting it into the corpus.
